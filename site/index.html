$_ Generated Secrets Operator

Docs GitHub

Generate Kubernetes Secrets in-cluster: passwords, tokens, SSH keys. Declared next to your app; the values are never stored in Git.

Try it in 5 minutes GitHub

Demo

Why

  1. Helm's randAlphaNum with lookup generates a new value under Argo CD and helm template, because lookup returns nothing there.
  2. Encrypting a password with SOPS (Secrets OPerationS) or Sealed Secrets adds key management when no human needs to know the password.
  3. A pipeline that exists only to generate a key is a pipeline to maintain.

The one promise: a value changes only when you decide — you change its definition, delete the Secret (or one key), or configure a rotation. It does not change when the operator restarts or is upgraded, when its cache is lost, or when you re-apply the same manifest.

Try it in 5 minutes

You need kind, Helm 4 and kubectl; no clone is needed. The kind image below runs Kubernetes 1.34, the oldest supported version.

shell 
kind create cluster --image kindest/node:v1.34.11@sha256:44e222ee2132dab25ff87301682f89eb82c7880ea3a1bf543bfe9708fd08d67d
helm repo add jabbas https://jabbas.github.io/helm-charts
helm repo update jabbas
helm install generated-secrets-operator jabbas/generated-secrets-operator --namespace generated-secrets-system --create-namespace --wait
kubectl apply -f - <<'EOF'
apiVersion: generatedsecrets.jabbas.eu/v1alpha1
kind: GeneratedSecret
metadata:
  name: app-admin
spec:
  deletionPolicy: Retain
  data:
    username: admin
  fields:
    - name: password
EOF
kubectl wait --for=condition=Ready gensecret/app-admin --timeout=60s
kubectl get secret app-admin -o jsonpath='{.data.password}' | base64 -d; echo

Restart the operator and read the password again; it stays the same:

shell 
kubectl rollout restart deployment/generated-secrets-operator -n generated-secrets-system
kubectl rollout status deployment/generated-secrets-operator -n generated-secrets-system
kubectl get secret app-admin -o jsonpath='{.data.password}' | base64 -d; echo

Clean up:

shell 
kind delete cluster

The HTTP chart repository is not signed; for the cosign-signed chart and how to verify it, see Installation.

When to use it, and when not

Use it for

Secrets a machine can invent: passwords, tokens, random keys, SSH key pairs, basic-auth credentials.

Do not use it when

  • The secret is issued by someone else (a vendor API key, another team's password).
  • The value must be known before deployment, or be identical across clusters.
  • The values must survive losing the cluster. They live only in the cluster, in etcd (the Kubernetes data store); back up the Secrets, for example with Velero.

Other tools fit other jobs:

  • Sealed Secrets, SOPS: encrypt values a human already has, to commit them to Git.
  • External Secrets Operator: syncs secrets from an external store; right when that store is the source of truth.
  • HashiCorp Vault, OpenBao: a full secrets platform; heavy if you need only a few generated passwords.
  • Helm randAlphaNum + lookup: the value is regenerated under helm template and Argo CD.

Generated values are ordinary Secrets: readable with get secrets, and unencrypted in etcd unless encryption at rest is enabled (see Security).
